大模型推理的性能瓶颈，很多时候并不在算力，而在 **KV Cache**。这篇笔记从「它为什么存在」讲起，再梳理围绕它的全生命周期优化。

## 一、为什么需要 KV Cache

大语言模型是**自回归**生成的：每产生一个新 token，都要拿它和前面所有 token 做注意力计算。如果不做缓存，每生成一个 token 就要把整段历史重新算一遍 K、V，计算量随长度急剧膨胀。

KV Cache 的思路很直接：把历史 token 的 **Key 和 Value 缓存下来**。生成新 token 时，只需为它单独计算 Query，再与缓存中的 K、V 做注意力，从而避免重复计算。这是现代推理系统的标配，也是解码阶段提速的关键。

代价是显存：缓存会随上下文长度**线性增长**。在长上下文场景下，即便用 8bit 量化，单请求的 KV Cache 也可能高达数十 GB，严重挤压并发能力。

## 二、长上下文的两大挑战

1. **Prefilling 的计算延迟。** 注意力对上下文长度是平方级复杂度，预填充阶段延迟极高。论文给出的例子是：在单张 A100 上推理 8B 模型、处理 100 万 token，可能超过 30 分钟。要把 1M token 做到几十秒级响应的 API，往往需要数十张 GPU。
2. **KV Cache 的存储压力。** 如上一节所述，长上下文下缓存动辄数十 GB，既压制并发，也推高部署成本。

## 三、以 KV Cache 为中心的推理流程

真实服务往往同时处理多个请求，因此**跨请求优化**格外重要。一个典型流程可以拆成几个阶段：

- **Prefilling**：请求到达后计算初始 KV Cache，可用 MInference 等高效计算策略降低延迟；
- **存储**：写入显存/内存前可做压缩，减少空间；
- **召回与加载**：Decoding 阶段从存储读取 KV Cache，可优化数据布局与预取，缓解内存瓶颈。

最典型的跨请求优化是 **Prefix Cache 复用**：不同请求常常共享同一段 system prompt 或上下文，复用这部分 KV Cache 能省掉大量重复计算。SGLang 早期用前缀树（prefix trie）查找可复用缓存，新版本则倾向用哈希判断是否命中，鲁棒性更好。

更进一步的还有**语义级匹配**：当请求只差几个字或存在轻微编码差异时，完全匹配会失效，此时可通过最长公共前缀或语义相似度召回，再配合小范围重算，提高命中率。

## 四、KV Cache 的全生命周期优化

围绕 KV Cache，优化可划分为四个阶段：

1. **生成**：传统 Full Attention 计算量大。可做 Prompt 压缩、把标准 Attention 换成线性 Attention 等近似模块，或基于注意力的动态稀疏性只保留关键连接。
2. **压缩与存储前处理**：把 KV Cache 精度从 FP16 降到 INT8 甚至 2bit；同时移除不重要 token 的 KV，让存储与 token 重要性对齐。
3. **语义检索**：在缓存池复用时，用语义哈希、向量相似度替代完全匹配，并配合局部重算。
4. **解码加载优化**：解码阶段 KV Cache 加载受显存带宽限制，可通过 sparse load 缓解 memory-bound 问题。

## 五、关键观察：注意力的动态稀疏性

作者的一个重要发现是：**注意力本质上是高度稀疏的，且稀疏结构随上下文动态变化**。

- 在 128K 上下文中只召回 4K 的 KV Cache，稀疏率可达 **96.4%**，即约 3% 的 KV 就能恢复 95% 以上的 Attention Recall；
- 但把某个上下文激活的索引复用到另一上下文，稀疏召回率会从 96.4% 掉到 83.7%，说明稀疏性与具体上下文强相关；
- 这种稀疏性在空间上具有**局部性**，注意力矩阵常呈「A 形」（关注序列开头 + 当前位置附近）。此外还有**竖线模式**（强关注少量全局关键 token）、**斜线模式**（可能与 RoPE 的 N-gram 局部信息有关）、**块状局部模式**等。

这些结构规律为 GPU 上的细粒度、结构感知的稀疏加速提供了天然契机。

## 六、代表性工作

- **MInference 1.0**：分 Offline（为每个 Attention Head 搜索最优稀疏模式）与 Online（动态估计当前上下文的激活区域）两阶段，把稀疏模式融合进底层 kernel。最高约 **10 倍加速**，可将 60 张 A100 才能支撑的 1M token 服务压缩到 8 张单节点。
- **MMInference**：面向多模态。视频帧/图像 Patch 使注意力呈现规整的网格结构，却不适配擅长大块稠密计算的 Tensor Core。作者利用排列不变性对行列重排，把网格映射为块状结构；同时处理模态交错产生的「模态边界」，最终端到端最高约 **8.3 倍加速**。
- **RetrievalAttention**：针对向量索引在注意力中的 OOD 问题（Query 与 Key 分布不一致，要 95% 召回需扫描超 50% 的 Key）。采用 GPU + CPU 联合执行：Prefilling 时把 KV 搬到 CPU 构建索引，解码时在 CPU 查 top-K 并只算部分注意力，从而能在 RTX 4090 上做 128K 长文本推理。
- **SCBench**：统一建模多轮对话、企业文档反复查询等共享上下文模式，覆盖 12 个子任务、13 种长上下文建模方法与四类 KV Cache 优化策略，系统评估真实长上下文表现。

## 七、两点重要结论

- **支持多轮解码必须具备 O(n) 级内存。** 仅靠 token 级压缩，第一轮可能很好，但随着轮次增加性能会明显衰减——稳健的多轮响应需要保留完整上下文。
- **长文本生成存在分布漂移（distribution shift）。** 生成不同 token 时关注的上下文区域会发生显著迁移，可能导致语义不一致。对不同任务，性能衰减差异也很大：越细粒度、越依赖精确/语义匹配的任务，衰减越明显。

## 小结

KV Cache 既是长上下文推理的加速器，也是显存与带宽的主要瓶颈。把它当作一个完整的生命周期来看——生成、压缩存储、语义检索、解码加载——才有更大的优化空间。动态稀疏注意力、Prefix Caching 等方向，正在被 vLLM、SGLang 等主流框架和线上服务广泛采用。
